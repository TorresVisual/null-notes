# PDF Image Extraction Design

**Goal:** Extract embedded raster images (figures, diagrams, photos, screenshots) from a PDF's page content during import, placing each one in correct reading order relative to the surrounding text, instead of today's behavior — `extract.rs` reads only character glyphs, so every image on a page is silently dropped.

**Why now:** Third of four subsystems closing the gap with PDF import quality elsewhere (Notion cited as the comparison point when this effort started — see [[pdf-multi-column-reading-order-design]] and [[pdf-table-reconstruction-design]] for the first two). General structure-detection quality is the remaining one, independent, a separate future spec.

**Non-goals (out of scope for this spec):**
- **Vector-drawn figures** (plots, diagrams built from PDF path/line objects rather than an embedded raster image — common output from matplotlib, TikZ, etc). These have no "real" image to extract; capturing one means rendering and cropping that region of the page like a screenshot, an entirely different code path (reusing whole-page rasterization, but region-bounded) than direct object extraction. Deferred to a future pass.
- **Size/decoration filtering.** Every embedded raster image is extracted, including small decorative ones (a letterhead logo repeated on every page) — no minimum-dimension heuristic, per explicit choice over the alternative of filtering tiny images.
- **Meaningful alt text.** PDFs essentially never carry usable accessibility metadata for this document class (lecture slides, exercise sheets); alt text defaults to empty (`![](path)`), matching what a plain, unannotated image reference already round-trips through `NoteImage.tsx` correctly.
- **Full correctness on multi-column pages.** An image on a page the multi-column work (`columns::segment_regions`) has split into multiple regions is assigned to whichever region's x-extent contains it — a small, bounded lookup, not a redesign — but this is the one place these two subsystems touch, and isn't exercised by the real test document for this spec (single-column only).

## Background: what's missing today, and what already exists to build on

`extract.rs`'s `extract_pages_native` calls `page.text()` and iterates `text.chars()` only — nothing in the pipeline touches pdfium's page *object* API at all, confirmed by search: no `PdfPageObject`/`PdfPageImageObject` usage anywhere in the codebase. This is genuinely greenfield, unlike the multi-column and table work, which were pure `CharBox`-geometry problems layered on an existing extraction path.

Two things already exist and this spec builds directly on them rather than duplicating:

- **Frontend rendering and round-trip**: `src/editor/extensions/NoteImage.tsx` already defines a working `image` TipTap node. Its `src` attribute is a path *relative to the note*, resolved via `api.assets.read(notePath, src)`. It serializes to plain `![alt](src "title")` Markdown when no width/height is set, and parses that same syntax back — so a PDF importer that emits ordinary `![alt](path)` Markdown needs zero frontend changes to round-trip correctly.
- **Backend asset storage**: `src-tauri/src/commands/assets.rs` already has `write_note_asset(note_path, mime, data) -> Result<String, String>`, which creates a `{stem}.assets/` sidecar next to the note (matching the `NoteName.assets/` convention `CLAUDE.md`'s storage-boundary section already documents) and names files `image-{unix_millis}.{ext}`.

**The one real gap**: `import_pdf_markdown(pdf_path) -> Result<String, String>` runs and returns before the note file — and therefore its `.assets/` sidecar — exists; the note only gets created afterward in `ImportButton.tsx`. Writing extracted images to the right sidecar requires the Rust command to know the note's intended path up front. `import_pdf_pages` (the separate scanned-PDF "Pages mode" command) already takes a `note_path: String` parameter for exactly this reason — `import_pdf_markdown` needs the same.

## Architecture

**Extraction**: a new pass in `extract.rs`, alongside the existing text-character extraction, enumerates `page.objects()`, filters for `PdfPageObject::Image`, and for each one captures its bounds (in the same PDF user-space coordinates `CharBox`'s `x`/`y`/`top`/`bottom` already use — bottom-left origin, larger `y` higher on the page) and its pixel data, converted to PNG bytes through the `image` crate (already a dependency, already used for the whole-page-rasterization path in `renderer.rs`). The exact pdfium-render method for pulling bytes off a `PdfPageImageObject` (`get_raw_image`/`get_processed_image`, or equivalent — confirmed via the crate's own docs that page objects are enumerable and bitmap-to-`image::DynamicImage` conversion exists, but the precise method name needs pinning against the installed crate version) is an implementation-time detail, not a design blocker — consistent with how `MIN_GUTTER_EMS`-style constants were left for implementation-time tuning in prior specs here.

**Storage**: `write_note_asset`'s file-writing logic (directory naming, byte-writing, filename scheme) is factored into a plain, non-async Rust function that both the existing Tauri command and the new PDF-import path call directly — one place owns the `{stem}.assets/` convention, not two. `import_pdf_markdown` gains a `note_path: String` parameter, letting it create the sidecar and write image bytes into it *before* the `.md` file itself exists, exactly as `import_pdf_pages` already does for the scanned-PDF path. This assumes `ImportButton.tsx` can compute the note's intended path (from the PDF's filename, the same way it presumably names the note it creates immediately afterward) before calling this command rather than only after — a reasonable expectation given `import_pdf_pages` already does exactly this, but the implementation plan should confirm `ImportButton.tsx`'s actual current sequencing before assuming it's a small change.

**Reading-order interleaving**: reuses the same pattern proven for tables, but simpler — an image never wraps or merges with anything, so there's no growing-window algorithm needed. A new `Inline::ImageRef(path, alt)` becomes the sole content of a synthetic `Line`, whose `y` is the image's vertical center; these synthetic lines are appended to the `Vec<Line>` `group_lines` already produces from the page's text (which itself is completely unchanged — no new parameter, no touched internals), then the combined list is re-sorted by `y` before `group_blocks` runs. `classify` gains one more early check (mirroring the `TableRow` check), and `finish_block` gains a `Block::Image { path, alt }` arm; `blocks_to_markdown` renders it as `![alt](path)`, percent-encoding the path the same way the frontend's own markdown boundary already does for `.assets/` folder names containing spaces (reusing the `urlencoding` crate, already present in the dependency tree) — the PDF pipeline's Rust code produces the actual `.md` file's text directly, the same boundary `NoteImage.tsx`'s own `encodeSrc`/`decodeSrc` pair exists for.

## Edge cases

- An image pdfium can't decode cleanly is skipped, not fatal — one bad element doesn't break the rest of the page, the same philosophy that already lets a malformed equation render its own KaTeX error rather than corrupting the surrounding note.
- A page split into multiple regions by multi-column segmentation: each image is assigned to whichever region's x-extent contains its horizontal center (a direct reuse of the x-extent each region already computes during column detection — see Non-goals for why this isn't exercised by this spec's own real-document verification).
- No size/type filtering (see Non-goals) — every embedded raster image on every page becomes an asset file and an image reference.

## Testing

The `Inline::ImageRef`/`Block::Image`/`classify`/`blocks_to_markdown` additions are pure `Line`/`Block` logic — fully unit-testable in `layout_tests.rs` without pdfium, exactly like the table work's additions, by constructing synthetic `Vec<Line>` inputs including a manually-built image-carrying `Line` at a known `y` between two text lines and confirming it renders in the correct position.

The pdfium-dependent extraction itself (page-object enumeration, bounds, byte extraction) lives in `extract.rs` and isn't unit-testable without the native library, consistent with the rest of extraction — judged instead against a real document, per this pipeline's standing rule that every bug found so far was invisible in synthetic fixtures alone.

**Real-document verification is required before this feature is considered done.** A test PDF already exists for this: `notes/image_test.pdf` (generated via `.null/scratch/generate_image_test_pdf.py`), containing a gradient image between two paragraphs on page 0 (the reading-order check: it must land between them, not before or after both) and a standalone labeled figure after a heading on page 1. The implementation plan's verification step re-runs the standard `NULL_NOTES_PDF=../notes/image_test.pdf cargo test dump_markdown -- --ignored --nocapture` diagnostic and confirms: both images appear in the correct textual position, the written PNG files are non-trivial and roughly match the known source dimensions (300×200 and 400×250), and the generated `![](path)` references use the same path shape (`{stem}.assets/image-*.png`, percent-encoded) `NoteImage.tsx` already expects.
