# PDF Image Extraction Design

**Goal:** Extract embedded raster images (figures, diagrams, photos, screenshots) from a PDF's page content during import, placing each one in correct reading order relative to the surrounding text, instead of today's behavior — `extract.rs` reads only character glyphs, so every image on a page is silently dropped.

**Why now:** Third of four subsystems closing the gap with PDF import quality elsewhere (Notion cited as the comparison point when this effort started — see [[pdf-multi-column-reading-order-design]] and [[pdf-table-reconstruction-design]] for the first two). General structure-detection quality is the remaining one, independent, a separate future spec.

**Non-goals (out of scope for this spec):**
- **Vector-drawn figures** (plots, diagrams built from PDF path/line objects rather than an embedded raster image — common output from matplotlib, TikZ, etc). These have no "real" image to extract; capturing one means rendering and cropping that region of the page like a screenshot, an entirely different code path (reusing whole-page rasterization, but region-bounded) than direct object extraction. Deferred to a future pass.
- **Size/decoration filtering.** Every embedded raster image is extracted, including small decorative ones (a letterhead logo repeated on every page) — no minimum-dimension heuristic, per explicit choice over the alternative of filtering tiny images.
- **Meaningful alt text.** PDFs essentially never carry usable accessibility metadata for this document class (lecture slides, exercise sheets); alt text defaults to empty (`![](path)`), matching what a plain, unannotated image reference already round-trips through `NoteImage.tsx` correctly.
- **Full correctness on multi-column pages.** An image on a page the multi-column work (`columns::segment_regions`) has split into multiple regions is assigned to whichever region's x-extent contains it — a small, bounded lookup, not a redesign — but this is the one place these two subsystems touch, and isn't exercised by the real test document for this spec (single-column only).

## Background: what's missing today, and what already exists to build on

`extract.rs`'s `extract_pages_native` calls `page.text()` and iterates `text.chars()` only — nothing in the pipeline touches pdfium's page *object* API at all, confirmed by search: no `PdfPageObject`/`PdfPageImageObject` usage anywhere in the codebase. This is genuinely greenfield, unlike the multi-column and table work, which were pure `CharBox`-geometry problems layered on an existing extraction path.

Two things already exist and this spec builds directly on them rather than duplicating:

- **Frontend rendering and round-trip**: `src/editor/extensions/NoteImage.tsx` already defines a working `image` TipTap node. Its `src` attribute is a path *relative to the note*, resolved via `api.assets.read(notePath, src)`. It serializes to plain `![alt](src "title")` Markdown when no width/height is set, and parses that same syntax back — so a PDF importer that emits ordinary `![alt](path)` Markdown needs zero frontend changes to round-trip correctly.
- **Backend asset storage**: `src-tauri/src/commands/assets.rs` already has `write_note_asset(note_path, mime, data) -> Result<String, String>`, which creates a `{stem}.assets/` sidecar next to the note (matching the `NoteName.assets/` convention `CLAUDE.md`'s storage-boundary section already documents) and names files `image-{unix_millis}.{ext}`.

**The one real gap, and how it's resolved**: `import_pdf_markdown(pdf_path) -> Result<String, String>` runs and returns before the note file — and therefore its `.assets/` sidecar — exists; `ImportButton.tsx` deliberately converts *before* creating the note, specifically so a PDF that turns out unconvertible never leaves an empty note behind (an explicit, documented property in the current code, confirmed by reading it directly). Threading a `note_path` into the conversion step to let Rust write assets directly would mean creating the note first, regressing that guarantee.

Instead: `import_pdf_markdown` writes no files and needs no note path at all. It returns the markdown text with each image referenced by a synthetic placeholder (`![](pdf-image://0)`, `pdf-image://1`, …) plus a parallel list of `{ placeholder, mime, data }` — the same `data: number[]` byte shape `api.assets.write` already accepts. `ImportButton.tsx`, after creating the note (unchanged timing), loops over the returned images, calls the existing `api.assets.write(note.path, mime, data)` once per image exactly as `NoteImage.tsx`'s own paste/drop handler already does, and substitutes each returned real path — run through `NoteImage.tsx`'s own exported `encodeSrc` — for its placeholder in the markdown before saving. This needed no Rust-side asset-writing code, no percent-encoding in Rust, and no command-signature changes to `import_pdf_markdown`'s *input* (only its return type, from `String` to a small struct) — a smaller, safer design than the original note-path-threading sketch, found by reading `ImportButton.tsx` directly rather than assuming its sequencing.

## Architecture

**Extraction**: a new pass in `extract.rs`, alongside the existing text-character extraction, enumerates `page.objects()`, filters for `PdfPageObject::Image`, and for each one captures its bounds (in the same PDF user-space coordinates `CharBox`'s `x`/`y`/`top`/`bottom` already use — bottom-left origin, larger `y` higher on the page) and its pixel data. Confirmed directly against the installed `pdfium-render 0.9.2` source (not just its docs): `PdfPageImageObject::get_processed_bitmap(&document)` returns a `PdfBitmap` (accounting for filters/masks/transforms applied to the object) with **no `image_api` feature required** — `.as_rgba_bytes()` gives raw pixels, which `image::RgbaImage::from_raw(...).save(...)` (already a dependency) turns into PNG bytes. This is the exact same conversion path `renderer.rs`'s whole-page rasterization already uses, for the same reason noted in its own comment: pdfium-render's optional `image_api` feature pulls in a separately-versioned `image` crate whose PNG encoder isn't compiled in by default. `PdfPageObjectCommon::bounds()` (a blanket-implemented trait method, so it needs the trait in scope — already the case via `pdfium_render::prelude::*`, the same import `renderer.rs` already uses) gives a `PdfQuadPoints`, whose `.left()`/`.bottom()`/`.right()`/`.top()` read off directly, mirroring how `CharBox` extraction already reads `bounds.left().value` etc. from `loose_bounds()`.

**Reading-order interleaving**: reuses the same pattern proven for tables, but simpler — an image never wraps or merges with anything, so there's no growing-window algorithm needed. A new `Inline::ImageRef(placeholder, alt)` becomes the sole content of a synthetic `Line`, whose `y` is the image's vertical center; these synthetic lines are appended to the `Vec<Line>` `group_lines` already produces from the page's text (which itself is completely unchanged — no new parameter, no touched internals), then the combined list is re-sorted by `y` before `group_blocks` runs. `classify` gains one more early check (mirroring the `TableRow` check), and `finish_block` gains a `Block::Image { placeholder, alt }` arm; `blocks_to_markdown` renders it as `![alt](placeholder)` — the placeholder travels through unmodified, since it isn't a real path yet and needs no escaping.

## Edge cases

- An image pdfium can't decode cleanly is skipped, not fatal — one bad element doesn't break the rest of the page, the same philosophy that already lets a malformed equation render its own KaTeX error rather than corrupting the surrounding note.
- A page split into multiple regions by multi-column segmentation: each image is assigned to whichever region's x-extent contains its horizontal center (a direct reuse of the x-extent each region already computes during column detection — see Non-goals for why this isn't exercised by this spec's own real-document verification).
- No size/type filtering (see Non-goals) — every embedded raster image on every page becomes a pending image (and, once the frontend writes it, an asset file) and an image reference.

## Testing

The `Inline::ImageRef`/`Block::Image`/`classify`/`blocks_to_markdown` additions are pure `Line`/`Block` logic — fully unit-testable in `layout_tests.rs` without pdfium, exactly like the table work's additions, by constructing synthetic `Vec<Line>` inputs including a manually-built image-carrying `Line` at a known `y` between two text lines and confirming it renders in the correct position.

The pdfium-dependent extraction itself (page-object enumeration, bounds, byte extraction) lives in `extract.rs` and isn't unit-testable without the native library, consistent with the rest of extraction — judged instead against a real document, per this pipeline's standing rule that every bug found so far was invisible in synthetic fixtures alone.

**Real-document verification is required before this feature is considered done.** A test PDF already exists for this: `notes/image_test.pdf` (generated via `.null/scratch/generate_image_test_pdf.py`), containing a gradient image between two paragraphs on page 0 (the reading-order check: it must land between them, not before or after both) and a standalone labeled figure after a heading on page 1. Since asset-writing now happens entirely on the frontend (see Architecture), the Rust-only diagnostic verifies what Rust is actually responsible for: the `dump_markdown`-style diagnostic confirms both images' placeholders appear in the correct textual position (between the two paragraphs; after the heading), and a small dedicated diagnostic confirms the extracted image bytes are non-trivial and roughly match the known source dimensions (300×200 and 400×250) — decodable back into an image, not garbage bytes. The frontend placeholder-substitution step (`ImportButton.tsx`) is small enough to be covered by its own unit/integration test rather than needing a second real-document pass.
