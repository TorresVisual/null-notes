# Search shows at most 20 results and offers no sort order

## Summary
Show all matches (loaded as the user scrolls) and let the user sort by relevance, modified time or name.

## Problem
In a workspace with a few hundred notes a common word matches more than 20 notes. The list silently stops at 20 and the ranking is the only ordering, so the one note the student wants can be unreachable.

## Competitor reference
[Search](https://obsidian.md/help/plugins/search) offers sorting by file name, modified time and created time and shows the full result list.

## Current behavior
`db/notes.rs:210-214` appends `ORDER BY rank LIMIT 20` (or `ORDER BY n.updated_at DESC LIMIT 20` with no free text). `SearchResult` carries no timestamp, and `SearchModal.tsx` has no sort control or load-more.

## Expected behavior
Results beyond the first page are reachable, with a visible count; a sort control offers relevance, recently modified and name (A-Z).

## Acceptance criteria
- [ ] A query with more than 20 matches lets the user reach every match (paged or incremental load)
- [ ] The UI states the total match count
- [ ] Sort options: relevance (default for text queries), modified new-to-old, name A-Z; the choice persists for the session
- [ ] Keyboard navigation and jump-to-match behaviour (#19) are unchanged
- [ ] Result queries stay under the 100 ms budget at a few hundred notes (ROADMAP §5)

## Scope
**In:** Result paging/sorting for the Ctrl+K search modal.

**Out (track separately):** New query syntax (D02), copy-results and explain-query actions.

## Implementation considerations
Add `updated_at` to `SearchResult` (the `notes` table already has it), parameterise LIMIT/OFFSET in `search_notes`, and have `SearchModal.tsx` request further pages. Natural sort of names is tracked in #123.

## Priority
P2. Hard-capped results hide matching notes with no signal that anything is missing.
