# Notes with YAML frontmatter are rewritten and corrupted when edited

## Summary
A note that starts with a YAML frontmatter block must come back byte-for-byte unchanged after it is opened and edited. This is about not damaging the header, not about adding a properties UI.

## Problem
The editor parses the frontmatter as Markdown: markdown-it reads `---` as a horizontal rule, the key lines as a paragraph and the closing `---` as another rule. On the next autosave the serializer writes that back as different text.

## Competitor reference
Obsidian stores properties as YAML at the top of the file ([Properties](https://obsidian.md/help/properties)). Any app that opens the same folder must leave that block alone. Null Notes already treats a workspace as a plain folder of `.md` files, so opening an Obsidian vault is a realistic path.

## Current behavior
No frontmatter handling exists anywhere in `src/` or `src-tauri/src/` (ROADMAP §5 defers properties on purpose). Experiment with the editor stack (StarterKit + tiptap-markdown, same markdown-it):

```
---
title: Foo
tags: [a, b]
aliases:
  - Bar
---
```
round-trips to
```
---

title: Foo tags: \[a, b\] aliases:

- Bar

---
```
Newlines collapse, brackets are escaped and the list is detached, so the YAML no longer parses.

## Expected behavior
Opening and editing a note with a leading YAML block leaves that block unchanged on disk. The block is not shown as document content. Raw (source) view shows it.

## Acceptance criteria
- [ ] A note starting with `---\n...\n---\n` loads without the block appearing as an hr/paragraph in the WYSIWYG view
- [ ] After typing in the body and autosaving, the frontmatter text on disk is byte-identical, including list items, brackets, quotes, comments and CRLF line endings
- [ ] Raw view shows and can edit the block; switching views does not alter it
- [ ] Title (`title_from_content`), tags (`extract_tags`), links (`extract_links`) and FTS indexing ignore the block, so a `tags:` or `title:` key neither creates tags nor becomes the title
- [ ] The external-change check and echo detection compare the full file content including the block (no false conflict bar)
- [ ] Unit tests cover the example above, an empty block, a block with `---` inside a string, and a note with no frontmatter

## Scope
**In:** Preserve the block verbatim across load and save.

**Out (track separately):** A properties editor, typed properties, property search and aliases (deferred by ROADMAP §5; track separately if that decision changes).

## Implementation considerations
Split the block off in the load path (`src/hooks/useNote.ts`, `src/editor/NoteEditor.tsx:102` setContent) and re-attach it on save; keep the save path invariants in CLAUDE.md (write_atomic, dirty buffer never overwritten, own-write echo). `src-tauri/src/commands/notes.rs` `title_from_content` (:61), `extract_tags` (:94) and `extract_links` (:113) must skip the block, as must the FTS body. `tiptap-markdown` has no frontmatter support, so this lives in our code.

## Priority
P1. Silent content corruption of user data; any note imported from an Obsidian vault, Jekyll/Hugo site or similar carries frontmatter.

Foundation (data integrity)
